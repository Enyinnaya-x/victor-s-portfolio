Confessions of an OG PHP Guy: Why I Now Run Most of My Work on Node.js and TypeScript

I used to clown JS developers in online bants, convinced the backend was no place for them. Turns out I was the one who needed educating — and Node.js, with TypeScript riding shotgun, changed my mind for good.

I have to own this one upfront: I used to be a big PHP guy, in the loud, tribal, "my language is more serious than yours" sense. I'd jump into online bants just to clown JavaScript developers — the running joke was that JS wasn't a "real" backend language and that people who used it on the server weren't quite in the same league as those of us running an "original" backend stack. I said it, I believed it, and I probably made it somebody's day worse in a comment section somewhere.

Looking back, that opinion wasn't actually mine. It was borrowed. I'd absorbed it from years of language-war content on social media — the kind of posts designed purely to farm engagement by pitting one camp against another — and I repeated it as if I'd arrived at it through my own technical judgment. I hadn't. I was just brainwashed, the same way a lot of devs get brainwashed into picking a side before they've actually built anything meaningful with the "other" side's tools.

The Bants Were Never the Argument

The irony is that none of those arguments were ever really about engineering. They were about identity. "Real backend devs use X" is a tribe statement, not a technical one. It doesn't survive contact with an actual production system, because a database doesn't care what language is talking to it, and neither does a payment gateway, a queue, or a client waiting on a response. They only care whether the system in front of them is correct and fast enough.

So at some point — pushed along by project requirements, deadlines, and clients who simply wanted one language across their whole stack — I actually sat down and built real things in Node.js. Not toy scripts. Production APIs, background workers, integrations with third-party services, the unglamorous plumbing that backend work is mostly made of. And the stack held up. Every time.

What Actually Changed My Mind

It wasn't one big revelation. It was a pile of small, repeated experiences that added up:

  • The async I/O model just fits most backend work. A huge share of what a backend does all day is wait — on a database, a third-party API, a file, a queue. Node's event loop is built for exactly that, and it does it without me reaching for threads or workarounds to get decent throughput.
  • One language, one head-space. Writing the API and the frontend in the same language means less context-switching, shared types between client and server, and a smaller mental tax every time I move between layers of the stack.
  • The ecosystem is enormous and mostly good. Whatever the integration — payments, queues, cloud SDKs, auth providers — there's almost always a well-maintained npm package already solving it, which means less time reinventing plumbing and more time on the actual business logic.
  • It's genuinely fast to iterate in. Spinning up a service, wiring a route, shipping a fix — Node.js gets out of my way in a manner I didn't expect, coming from a "configure everything up front" mindset.

TypeScript Closed the Gap

If I'm honest, plain JavaScript alone probably wouldn't have fully won me over. Some of the old "not a serious language" bias was really a reaction to untyped code — the kind of codebase where anything can be anything, and a typo three files away blows up in production instead of at compile time. TypeScript is what actually closed that gap for me. It gives the backend the kind of structure and compile-time guarantees that PHP veterans like me instinctively look for, without giving up any of the things that make the Node ecosystem great.

A small example of the kind of thing that used to make me nervous about JS on the backend, and how TypeScript just removes the worry:

order-service.tsTypeScript
interface OrderPayload {
    sellerId: string;
    sku: string;
    quantity: number;
}

// The compiler stops a bad call before it ever reaches the database —
// no runtime surprise three services downstream.
async function placeOrder(payload: OrderPayload): Promise<void> {
    if (payload.quantity <= 0) {
        throw new Error('quantity must be positive');
    }

    await db.transaction(async (trx) => {
        await trx('inventory')
            .where({ sku: payload.sku })
            .decrement('stock', payload.quantity);

        await trx('orders').insert(payload);
    });
}

That's the same discipline I'd apply writing a strict-typed PHP file or a Spring Boot service — just expressed in TypeScript instead. The types catch the dumb mistakes before they ship. The runtime stays fast and simple. It stopped feeling like I was giving anything up.

Where I Land Today

Most of my work now runs on Node.js with TypeScript. It's simple, it's quick to build and iterate in, and overall it's just been great to work with day to day — I'd genuinely recommend it to anyone building backend systems, including the PHP-brained version of me from a few years ago.

That doesn't mean I've swapped one dogma for another. If I'm picking up a new project, I still look at the actual requirements first — the concurrency model, the team's existing stack, the hosting constraints, whether PHP/Laravel or Spring Boot/Java is a better fit for that specific system. But honestly, for most of what crosses my desk, Node.js and TypeScript are a strong default, and I no longer need a reason to defend using them.

The stack war I used to participate in was never really about technology — it was about identity, dressed up as a technical opinion. Pick your tools for the job in front of you, not for the bants.

If you're evaluating a backend engineer and wondering whether their stack of choice says anything meaningful about their skill — it mostly doesn't. Ask what they shipped, what broke, and how they fixed it. That's the real signal, whether the language on the job was PHP, Java, or TypeScript.
